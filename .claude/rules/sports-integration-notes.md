# Sports integration notes

*Last touched 2026-10-18. Which additional team sports were investigated for `espnTeamSportService`/`cricketService`, and why some didn't make the cut.*

Investigated on 2026-09-16 while adding NRL and WNBA (both shipped — see `CLAUDE.md` for the code-level quirks: NRL's id-keyed logo CDN, its scoreboard endpoint rejecting date ranges, its lack of ESPN colour data).

**MLS — shipped 2026-09-30** as `MLS` (`soccer/usa.1`, team IDs `mls-{espn abbr}`), grouped under North America. Its old disqualification (empty `/standings` response) turned out to be the same site/v2-standings-is-broken-for-everyone issue fixed 2026-09-27 — `apis/v2` returns a full 30-row table (East/West conferences, same shape as NFL/NHL/MLB/WNBA, same known interleaving in League Overview). 30 clubs, all unique ESPN abbreviations, no name-substring collisions, no placeholder colours (checked programmatically, not just by eye) — the four clubs whose primary colour is genuinely `#000000` (Columbus Crew, D.C. United, LAFC, Minnesota United) each have a distinct real alternate colour, confirmed not to match the placeholder pattern. Verified live: all 30 resolve to distinct ids with real, mutually consistent results (e.g. Chicago 1-0 Charlotte from both sides) plus real next fixtures and ladder positions.

**Rugby union — not investigated in depth.** ESPN's core API lists 25+ separate rugby union competitions (Six Nations, Rugby Championship, URC, Premiership Rugby, etc.) with no single obvious "the" league the way NRL has exactly one. Would need a decision on which specific competition(s) to add, not just a slug lookup.

**F1 — technically has ESPN "team" data (constructors), but doesn't fit the app's data model.** No opponent, no win/loss record — just a points table and a race calendar. Would need a genuinely different card type, not a config addition.

**Update 2026-09-17 — more candidates checked, plus a universal bug found along the way:**

While researching further additions, found that ESPN's `/scoreboard?dates=X-Y` range query started 400ing for *every* league (NFL/AFL/NHL/MLB/NRL alike) — not an NRL-specific quirk as first thought. This was live-broken in production at the time (silently emptying the Today feed / league overview for every ESPN-routed league) and was fixed same-day by dropping the date param entirely everywhere (commit `260e35a`). If a future add hits this again, check whether ESPN restored range support before reintroducing per-league special-casing.

**Liga MX and Brasileirão — shipped 2026-09-19** (commit `9ece64f`). Same pipeline, this time with the scoreboard/schedule endpoints actually checked up front (both healthy) rather than left as a known gap. Confirmed live: América's and Flamengo's real results, correct logos, real fixtures from both scoreboards.

**Argentina (Liga Profesional), Saudi Pro League, and Primeira Liga — shipped 2026-09-20** (commit `c34d47c`), plus 4 other national leagues verified viable but not shipped (Turkey, Scotland, Japan, Belgium — user chose "2-3 biggest names" over all 7). Argentina's roster (30 teams, the biggest yet) has a real data quirk worth knowing about: ESPN's own data has two different clubs sharing the literal abbreviation "RIV" (Independiente Rivadavia and River Plate). Resolved by routing Independiente Rivadavia through abbreviation matching (it happens to be the first "RIV" in ESPN's own list, so this resolves to itself) and forcing River Plate through the existing name-based fallback instead (safe for "River Plate" — no other club's name collides with it). Verified live: all three of River Plate, Independiente Rivadavia, and plain "Independiente" (a *third*, separate club whose name is a literal substring of Independiente Rivadavia's) resolved to their own correct, distinct real results — this is the kind of collision worth checking for by hand in any large single-country roster, not just trusting the general abbreviation/name fallback to sort itself out.

At this point every soccer-shaped ESPN league checked so far has shipped cleanly — the remaining unshipped candidates below are all disqualified for structural reasons (bad standings data, no matching league, wrong data shape), not because they weren't gotten to yet.

**Turkish Süper Lig and Scottish Premiership — shipped 2026-09-21** (commit `d9a0744`). Scotland's roster forced a real fix, not just a workaround: ESPN's own data has two clubs sharing the abbreviation "DUN" (Dundee, Dundee United), and unlike Argentina's case there's no abbreviation-only escape hatch — any "DUN"-equal abbreviation resolves to whichever team ESPN lists first regardless of which is meant, and "Dundee" is a genuine substring of "Dundee United"'s own name. Fixed **in the shared `findTeamByName()` matching function itself** (not a per-league workaround): it now checks every team for an exact name match before ever trying a fuzzy substring one. This is a general improvement, not Scotland-specific — retroactively also covers Argentina's Independiente/Independiente Rivadavia case via the same mechanism. Verified live: Dundee and Dundee United each resolved to their own correct, distinct real results.

**Lesson for any future large or single-country roster:** always scan for two things by hand before shipping — (1) two teams sharing the same ESPN abbreviation, and (2) one team's name being a literal substring of another's (e.g. "Dundee" inside "Dundee United", "Independiente" inside "Independiente Rivadavia"). Case (1) alone is solvable per-team (River Plate model); case (2) combined with (1) needs the exact-match-first fix already in place, not another workaround.

**Drawn-match outcomes always shown as a definite win or loss — found and fixed 2026-10-12 while live-verifying the La Liga roster sync above.** Three of the five new La Liga clubs' real results came back tied (Málaga 1-1, Elche 0-0, Racing Santander 2-2) but each rendered `"outcome":"L"`, which is logically impossible. football-data.org's real `score.winner` value for a drawn match is the literal string `'DRAW'` — confirmed via a raw API call — not `null`. Both `footballService.js` and `worldCupService.js` only ever checked `winner === null` for a draw, so every real draw fell through to the win/loss ternary; this affects every football-data.org-routed league (EPL, La Liga, Bundesliga, Serie A, Ligue 1, Championship, Eredivisie, UCL) and the World Cup, not just La Liga. The existing unit test for this used `winner: null` mock data, matching the code's wrong assumption rather than the real API shape, which is why it went uncaught until a live check surfaced it. Fixed both services to check `winner === 'DRAW' || winner === null` (null kept as a defensive fallback); existing tests corrected to use the real `'DRAW'` value with a separate test added for the `null` fallback; re-verified live post-fix that Málaga/Elche/Racing Santander all now correctly show `"outcome":"D"`.

**Also found and fixed, on an unrelated still-present entry: a second matching-bug class beyond the accent-folding fix from 2026-10-09.** The stored "Bodo/Glimt" (plain ASCII o) never matched `findFDTeam` — the real club is "FK Bodø/Glimt". If another ø/đ/ł-type letter trips this again elsewhere, the same fix applies: match the real spelling, don't fight the fold.
